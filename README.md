## 📚 학습 내용

### 1. 게임 구조 (Canvas 게임의 기본 뼈대)

```
입력(키보드/터치) → update(dt): 물리 계산 → draw(): 화면 그리기 → requestAnimationFrame 반복
```

- `requestAnimationFrame`으로 매 프레임마다 `update` → `draw`를 반복한다.
- `dt`(지난 프레임과의 시간 차이)를 써서 컴퓨터 성능과 관계없이 같은 속도로 움직이게 한다.
- 화면 크기에 맞춰 캔버스를 확대/축소하고, `devicePixelRatio`로 고해상도 화면에서도 선명하게 그린다.

### 2. 게임 요소

| 요소 | 역할 | 점수 |
|---|---|---|
| 플리퍼 (좌/우) | 공을 쳐 올림 | – |
| 플런저 | 누르고 있다가 떼면 공 발사 (오래 누를수록 강하게) | – |
| 범퍼 3개 | 닿으면 공을 튕겨냄 | 100 |
| 슬링샷 2개 | 플리퍼 위 삼각형, 공을 옆으로 튕김 | 10 |
| 상단 롤오버 레인 3개 | 모두 켜면 배수(MULT) +1 (최대 x5) | 50 (+1000) |
| 드롭 타깃 3개 | 맞으면 쓰러짐, 전부 쓰러뜨리면 보너스 | 250 (+5000) |

### 3. 물리 구현 핵심 개념

- **중력:** 매 순간 `vy += G * dt` → 공이 아래로 가속된다.
- **벽 = 선분:** 공(원)과 선분 사이의 **가장 가까운 점**을 구해, 거리가 반지름보다 작으면 충돌로 판정한다.
- **반사:** 충돌면의 법선 벡터 `n` 방향 속도 성분을 뒤집는다.
  `v = v - (1 + e) * (v·n) * n` (e = 반발 계수, 0이면 안 튀고 1이면 완전히 튐)
- **움직이는 플리퍼:** 플리퍼가 회전하는 속도(각속도 × 회전축으로부터의 거리)를 더해서 계산해야 공이 세게 날아간다.
- **서브스텝:** 한 프레임을 10번으로 쪼개서 계산 → 빠른 공이 벽을 뚫고 지나가는 현상(터널링)을 막는다.
- **일방통행 게이트:** 공이 어느 쪽에 있는지(외적의 부호)를 보고, 한쪽에서만 충돌하게 만든다.

### 4. Git & 배포 흐름

```bash
git add index.html
git commit -m "Add neon pinball web game"
git branch -M main                                   # 기본 브랜치 이름을 main으로
gh repo create pinball --public --source . --push    # GitHub 저장소 생성 + 업로드
gh api -X POST repos/<계정>/pinball/pages \
  -f "source[branch]=main" -f "source[path]=/"       # GitHub Pages 켜기
```

- GitHub Pages는 저장소의 `index.html`을 그대로 웹사이트로 보여준다.
- 무료 계정은 **공개(public) 저장소**여야 Pages를 쓸 수 있다.
- 이후에는 `main`에 push만 하면 사이트가 자동으로 다시 배포된다.

## 🐞 문제 해결 기록 (트러블슈팅)

직접 플레이 대신, 브라우저(Edge)를 화면 없이 실행해서 **자동으로 공을 발사하고 플리퍼를 치는 테스트**를 돌려 버그를 찾았다.

| # | 문제 | 원인 | 해결 |
|---|---|---|---|
| 1 | 공을 발사하면 점수 0으로 바로 빠짐 | 공이 위쪽 둥근 벽을 따라 미끄러져 왼쪽 벽 → 배수구로 직행 | 왼쪽 위에 **킥커**를 달아 공을 게임판 안쪽으로 튕겨냄 |
| 2 | 공이 플리퍼 근처에 끼어서 멈춤 | 경사벽 끝과 플리퍼 축 사이에 작은 **홈**이 생김 | 경사벽 끝점을 플리퍼 윗면에 매끄럽게 이어지게 조정 |
| 3 | 빠진 공이 플리퍼 아래로 옆으로 날아감 | 플리퍼 아래쪽에 벽이 없었음 | 플리퍼 아래에 **에이프런 벽** 추가 |
| 4 | 테스트에서 공이 "멈춘" 것처럼 보임 | 버그가 아니라 테스트 봇이 플리퍼를 계속 들고 있었음(공 받치기) | 봇에 쿨다운을 넣어 테스트 수정 |

## 💡 배운 점 / 느낀 점

- 게임은 결국 **"입력 → 계산 → 그리기"의 반복**이다.
- 그럴듯한 물리는 **벡터(내적, 법선, 외적)** 몇 가지만 알아도 만들 수 있다.
- 눈으로 보기 전에 **자동 테스트로 숫자(점수, 위치, 멈춘 시간)를 확인**하면 버그를 빨리 찾을 수 있다.
- 버그처럼 보여도 **테스트 방법 자체가 잘못**됐을 수 있다 (4번 사례).
- `gh` CLI를 쓰면 저장소 생성부터 배포까지 터미널에서 몇 줄로 끝난다.
